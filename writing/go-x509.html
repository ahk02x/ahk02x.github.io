Two bytes each

By Amir Khademi

I was working on a personal project and found a bug in how Go reads certificates. A certificate the size of a small photo could cost a server about 24 MB of memory to read, before the server even decides whether to trust it. I reported it, and then I built something to block it.

What I found

A certificate can list extra names it's valid for, called Subject Alternative Names, or SANs. One kind of name is a URI. When Go's crypto/x509 package reads a certificate, it turns every URI name into its own object in memory, and it keeps all of them. There's no limit on how many a certificate can have, and an empty one is allowed. An empty URI takes 2 bytes in the certificate. The object Go makes for it takes a lot more.

So I made a certificate with 130,000 empty URIs. It's about 260 KB, which is close to the most one handshake can carry in Go: its TLS code caps a certificate message at 256 KiB. Reading it allocates about 24 MB and keeps about 20 MB. That's around 76 times the size of the certificate.

One test certificate with 130,000 empty URI names (Go 1.27.3)
WhatSize
The certificate itself260,216 bytes
Memory Go allocates to read itabout 24 MB
Memory Go keeps after reading itabout 20 MB (76x)
Per TLS handshake, server asking for client certificatesabout 27 MB

Why it matters for servers

Some servers ask the client to show a certificate too. That's called mutual TLS (mTLS), and it's common between internal services and in payment systems. In Go, crypto/tls reads the client's certificate before your own check runs. So even a server that rejects the client has already paid for reading it. In my test that was about 27 MB per handshake.

Reporting it

I sent it to the Go security team first, privately. They said it's not a security issue and that I could file it in the open, so I did: golang/go#82858. It has the numbers above and the short program that produces them, standard library only. From what I read in RFC 5280, a URI name shouldn't be empty, so rejecting empty ones could be one fix. A limit on how many names a certificate can carry could be another. What Go does about it is the Go team's call.

Building the guard

Filing the bug fixes nothing for a server running today. So I wrote certguard, a small Go library that looks at a client certificate's raw bytes before Go's parser reads them, and says no if the certificate is too big or carries too many names. The defaults are 16 KB and 64 names. Real client certificates carry a handful.

The check can't have the same problem, so certguard doesn't build anything per name. It walks the certificate's structure down to the list of names, reads each entry's type and length, counts it, and skips over the entry itself. With the default limits, my 260 KB test certificate is turned away on size before anything else. With the size limit lifted, so it has to count all 130,000 names, it still says no in 3 allocations. Either way it uses about 100 bytes of memory, instead of 24 MB.

  • Bad input on purpose. Tests feed it garbage, structures that never say how long they are, a SAN extension marked critical, and long runs of empty names, and check that it doesn't crash or hang.
  • Fuzzed. Go's fuzzer mutates real and broken certificates and checks that certguard never counts fewer names than Go's own parser keeps. My last run: 10.4 million inputs in a minute, no failures.
  • My own bugs. Two real ones turned up while I was hardening it: a certificate with a broken tail after its first names could slip through, and a length check could overflow on 32-bit machines. Both are fixed.

Where it sits is the whole thing

Most of the time went into one question: where can a check like this run before Go reads the certificate?

  • In VerifyPeerCertificate or VerifyConnection: too late. By the time those callbacks run, Go has already read the certificate. You can still log it or reject the connection, but the memory is already spent.
  • In front of the TLS layer, TLS 1.2 only: works. In TLS 1.2 the client's certificate travels in the clear, so you can screen the raw bytes first (example code in the repo, not part of the library). TLS 1.3 encrypts it, so this only protects anything if the server is pinned to 1.2. Otherwise an attacker just picks 1.3 and walks past it.
  • Behind a proxy that handles TLS: works for the Go service. The proxy passes the raw certificate along, the Go service only trusts that value when it comes from the proxy, and it screens it before reading it. The proxy needs its own size limits, and if the proxy is written in Go, it has the same problem.
  • Don't ask for a certificate you don't need. If a server doesn't request client certificates, Go never reads one. That's the simplest fix.

For TLS 1.3 servers that need client certificates, Go has no hook today that runs before the read, so certguard can't protect them. The README says so up front.

Where it stands

The issue is open on Go's tracker. certguard works and has tests. It's defensive only: it just says no. The code and the README are on GitHub: github.com/ahk02x/certguard.
