Memory as infrastructure

By Amir Khademi

Claude Code forgets everything between sessions, so it keeps notes. I treat those notes the way I treat any other state on my network: a schema, a linter, a nightly check against reality, and a repository. Every rule below exists because the version without it failed.

The memory is a directory of Markdown files. One file is one current fact about a machine, a project, or a way I want the agent to work. Each has front matter: a name that must equal the filename, a description that is the recall signal, and one of four types (user, feedback, project, reference). Missing front matter fails lint. That is fussy for a pile of notes, right up until the agent confidently acts on a fact that has been wrong for weeks.

The index is a list of triggers

One file, MEMORY.md, is loaded into every session; everything else costs nothing until opened. So the core index is a per-session tax, and it has a budget: the linter warns at 8 KB and refuses the commit at 12 KB. In August I cut it to about 8 KB; by October it was 19.8 KB, because every new memory landed in it. Now the core holds only the rails, the staged work and the hubs, plus one line per domain pointing at an index-<domain>.md that is opened on demand. It is 7.8 KB, roughly 1.9k tokens per session; the six domain indexes total about 16 KB and are paid only when used.

The rule that matters more: an index line is a trigger, not a summary. A title and the condition under which the agent should open the file, in 120 characters or fewer. Verify The Contract — read the real field/value/route first; unknown NEVER means healthy tells the agent when to stop and look. A paraphrase of the contents invites it to act on the paraphrase instead of opening the file.

Rewrite, don't append

The natural way to update a note is a dated section under the old one. In August I measured that across 107 memories: 34 contained supersede-or-correction language, and the home server's build record had 17 dated headers and had reached 53 KB, about 13k tokens for a single recall. An append-log presents dead facts with the same confidence as live ones, recall surfaces the file and not a diff, and whichever line is read first wins. A memory that needs 300 lines read and a judgment about which half is dead is worse than no memory, because it is trusted.

So a memory holds current truth only. When a fact changes, the wrong sentence is replaced and the old one deleted. The directory is a git repository with over 440 commits; that is where history lives. Dated headers are the smell: more than three fails lint, as does any file of 12 KB or more. Past about 8 KB a file is no longer one fact; cut dead state or split it.

A rule nobody runs is not a rule

The linter was correct from August, and the memory about it said to run it before every commit. For nine days nothing did, and seven memories blew past the old 20 KB cap. That is the whole case for hooks over instructions. memlint.py now runs from a tracked hooks/pre-commit and blocks the commit on an unindexed file, a link to a missing file, an index line over 120 characters, a dangling wikilink, too many dated headers, an oversized file, or anything that looks like a credential. It blocks on errors only: there are around 40 standing warnings, and a gate that fires every time gets bypassed. The credential check holds the SHA-256 of known-bad strings, never the strings, and never echoes a hit, because a secret echoed while hunting for it re-leaks into a transcript that gets archived.

An instruction nobody executes is not a control.

Staleness is the real damage

Size lint cannot see a wrong fact. In August the home server's container table in memory was four containers behind, and the Stream Deck memory described a key layout I had renamed nine days earlier. Neither tripped a lint. By October, 87 memories asserted live state nobody had re-checked in 30 days or more.

Two mechanisms now. The linter flags any memory that asserts live state (an IP address, a LIVE or DEPLOYED verdict, the words "verified" or "measured") and has not changed in git for 30 days; rails and the indexes are exempt, since they encode judgment, not the state of a machine. And a memory can carry its own check: a top-level verify: line with one read-only, non-interactive shell command that finishes in under 25 seconds, plus an optional expect: regex. memverify.py runs them nightly from cron and records VERIFIED, FAILED, UNREACHABLE or BLOCKED. A recent VERIFIED counts as fresh. FAILED means the memory is wrong or the thing is down, so look before repeating it; a one-line summary prints at session start, only when something failed.

BLOCKED is for commands on a never-run list: anything that writes, restarts, elevates, kills or pings. One Windows box drops ICMP, so ping lies about it; one macOS command pops a password box on my screen. The verifier cannot judge a claim's meaning, only whether the box still agrees with it.

Three layers and a recall tool

  • Memory. Current truth, hand-kept, in git.
  • Digest. Every past chat as plain text, rebuilt hourly from the archive. Grep it; never open a big one whole.
  • Distilled. Per-session decisions, facts, open items and memory candidates, extracted overnight by a small local model on the home server. Its output is a suggestion, not a memory.

A brain recall command searches all three at once. Each memory records the session it came from, so brain show opens a memory next to the conversation that produced it; 130 of 168 memories resolve that way. The standing rule: recall before asking me to repeat anything, and keep the fact in memory and the reasoning in the digest.

What it taught me

Most of the cost of an agent session is carrying context, not generating; when I measured mine, 85 percent of spend was context. An unindexed memory is one the agent will never recall. An over-long one costs more per recall than the whole core index. A stale one is trusted. Every control here is cheap, stdlib Python and a git hook, and each replaced a sentence that said "remember to". The sentences did not work. The hooks do.
