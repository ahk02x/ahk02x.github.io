The timer firing is not evidence

Every other Sunday at 04:30, one script on the hypervisor patches the home fleet: the containers, the Home Assistant VM, the monitoring box, the host itself and, last, the firewall. It gets no credit for running, only for a check after the reboot finding that everything came back.

It started in October, after a security fix on one container, done by hand. Patching one machine makes you ask when the rest were last patched. There was no routine. There was me, remembering. So I asked Claude Code for a fortnightly cycle covering the Proxmox host and whatever else needed one.

What "graded on evidence" means

A dashboard I keep lists every scheduled job on the fleet and grades each one on its own evidence. Each of its rules came from a time it gave a wrong answer. A job with no record of its last run grades unknown, not ok, because the host's cron directory once showed healthy with nothing behind it. A freshly written state file doesn't count as success either, because one watcher rewrote its own file on a failed run and looked green through a whole outage.

A schedule proves something was scheduled, never that it ran.

Here the timer ticking is the schedule. The evidence is a success stamp, one file holding one timestamp, written only when the verify step finds nothing wrong. The dashboard grades on that stamp, so a cycle that fired and broke something goes stale after about 17 days, like one that never fired. The timer itself fires every Sunday, and the cycle runs only when the last good one is at least 13 days old. A failed cycle writes no stamp, so it retries next Sunday on its own. "It ran" and "it worked" are different claims. Only the second one earns a green.

The order, and why

  1. Preflight. Check the storage pools are ONLINE. If the 02:30 backup is still running, wait up to 90 minutes. Record every failed systemd unit so that later only new ones count.
  2. Snapshot. One recursive ZFS snapshot of host root, every container and the Home Assistant disk. The newest three are kept.
  3. Containers. A full upgrade inside each running container.
  4. Home Assistant. Core only from a .1 release, backup first; the .0 of the month is held and reported. Then the OS, and a VM reboot.
  5. The monitoring box. Patches itself and reboots itself 60 seconds later if its kernel changed. The host waits until it answers on the new kernel.
  6. The host. Full upgrade, the default-headers meta-package, then DKMS rebuilds the NVIDIA module for the newest kernel. If it did not build, the reboot is held.
  7. The firewall. OPNsense firmware update; it reboots itself when base or kernel changed. Last, so every download above has finished before the LAN loses its gateway for about a minute.
  8. Host reboot. Only if a new kernel landed and the GPU module exists for it.
  9. Verify and report. After the reboot, wait up to 15 minutes for every autostart guest, check the GPU inside the two containers that use it, diff failed units against the preflight list, check the pools, and send one Telegram message that opens with "done" or "needs a look". The stamp is written only if the problem list is empty.

Two machines, two verbs

The monitoring box and the firewall are not Proxmox guests. They patch themselves when asked, over an SSH key that can do nothing else: a forced command, pinned to the host's address, that understands exactly two words, status and run. The firewall's web interface owns root's authorized keys, so that line is pasted through the GUI: the one manual step in the install.

Traps from doing it by hand

  • Headers. The NVIDIA driver on the host is a .run install registered with DKMS, and only the running kernel's headers were ever installed. A new kernel arrives, DKMS has nothing to build against, and the two containers that use the GPU boot without one. The fix is the default-headers meta-package plus a DKMS autoinstall for the new kernel; the script will not reboot unless modinfo finds the module. A stale kernel for two more weeks beats two GPU-less containers at five in the morning. Every time.
  • Cosmetic failures. The Debian trixie systemd upgrade inside unprivileged containers without nesting leaves three mount units failed, in three containers. Services run; /tmp is on disk. Both real fixes, enabling nesting or masking the units, were refused by Claude Code's permission classifier, one as weakening security and one as touching a shared resource. Both are my call, and both are still open. The script flags only units that were not already failed at preflight, because a report that cries the same wolf every fortnight teaches you to stop reading it.

What it does not touch

Three machines are left out on purpose, and every report says so at the bottom. The Mac, because macOS and Homebrew want a password and a major version bump could break a local media pipeline. A Raspberry Pi that rides in the car, rarely on the network and liable to lose power mid-write. A Windows machine, which has Windows Update. A machine you're reminded is unpatched is a decision. One you forgot is a hole.

Who installs it

Claude Code wrote the cycle and verified the dry run. It wouldn't install it, though. The install script puts a root-level key on the firewall and the monitoring box and arms unattended hypervisor reboots, and the permission classifier refused that, correctly. The agent writes the thing that reboots the fleet; the human runs the one command that arms it, the same line the on-call setup drew. Once the key is in, the first unattended cycle falls in November.

The whole thing is one Python script, three systemd units, two forced-command stubs and an install script. All I wanted was one rule: the only green on the dashboard comes from a check run after the reboot, on the machines that actually came back, against what was there before.
