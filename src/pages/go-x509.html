The Go certificate bug

I found a bug in how Go reads certificates. A certificate the size of a small photo could cost a server about 24 MB of memory to read, before the server even decides whether to trust it. I reported it, Go fixed it, and I built a library that blocks it on the Go versions people still run.

The certificate
260 KB
Go reading it
24 MB
certguard checking it
~100 bytes

What I found

A certificate can list extra names it's valid for, called Subject Alternative Names, or SANs. One kind of name is a URI. When Go's crypto/x509 package reads a certificate, it turns every URI name into its own object in memory and keeps all of them. There was no limit on how many a certificate could have, and an empty one was allowed. An empty URI takes 2 bytes in the certificate. The object Go makes for it takes a lot more.

So I made a certificate with 130,000 empty URIs. It's 260,216 bytes. Go caps the whole certificate message in a handshake at 256 KiB (262,144 bytes), so that's about as big as one can get. Reading it allocates about 24 MB and keeps about 20 MB. That's around 76 times the size of the certificate.

Why it matters for servers

Some servers ask the client to show a certificate too. That's called mutual TLS (mTLS), and it's common between internal services and in payment systems. In Go, crypto/tls reads the client's certificate before your own check runs. So even a server that rejects the client has already paid for reading it. In my test that was about 27 MB per handshake.

Reporting it

I sent it to the Go security team first, privately. They said it's not a security issue and that I could file it in the open, so I did: golang/go#82858. It has the numbers above and the short program that produces them, standard library only. From what I read in RFC 5280, a URI name shouldn't be empty, so I suggested rejecting empty ones, or capping how many names a certificate can carry.

Go fixed it on 12 November. Go now refuses to create a certificate with an empty name, and its parser ignores empty names, so the 76x is gone on Go's main branch. Go versions released before the fix still have it.

Building the guard

A fix upstream does nothing for a server on an older Go. So I built certguard, a small Go library that looks at a client certificate's raw bytes before Go's parser reads them, and says no if the certificate is too big or carries too many names. The defaults are 16 KB and 64 names. Real client certificates carry a handful. The Go fix only covers empty names. certguard also caps names that aren't empty.

The check can't have the same problem, so certguard doesn't build anything per name. It walks the certificate's structure down to the list of names, reads each entry's type and length, counts it, and skips over the entry itself. With the default limits, my 260 KB test certificate is turned away on size before anything else. With the size limit lifted, it still says no on the name count, in 3 allocations. Either way it uses about 100 bytes of memory, instead of 24 MB.

  • Bad input on purpose. Tests feed it garbage, structures that never say how long they are, a SAN extension marked critical, and long runs of empty names, and check that it doesn't crash or hang.
  • Fuzzed. Go's fuzzer mutates real and broken certificates and checks that certguard never counts fewer names than Go's own parser keeps. Last run: 10.4 million inputs in a minute, no failures.
  • Bugs found along the way. Two real ones turned up while hardening it: a certificate with a broken tail after its first names could slip through, and a length check could overflow on 32-bit machines. Both are fixed.

Where the check can run

Most of the time went into one question: where can a check like this run before Go reads the certificate?

Where a pre-parse check can sit, and whether it stops the memory cost
WhereStops it?Why
VerifyPeerCertificate or VerifyConnectionNoGo has already read the certificate by the time these run. You can still reject the connection, but the memory is spent.
In front of TLS, server pinned to TLS 1.2YesIn TLS 1.2 the client certificate travels in the clear, so the raw bytes can be screened first. Example code is in the repo. If the server allows 1.3, an attacker just picks 1.3.
Behind a proxy that handles TLSYes, for the Go serviceThe proxy passes the raw certificate along and the Go service screens it before reading it. The proxy needs its own limits, and a proxy written in Go has the same bug.
Server doesn't ask for client certificatesYesGo never reads one. The simplest fix if you don't need them.

A Go server that handles TLS 1.3 itself and asks for client certificates has no hook that runs before the read, so certguard can't protect it. The README says that up front.

Where it stands

Go fixed the empty-name case upstream. certguard works, has tests, and is on GitHub as v0.1.0. It's defensive only: it just says no. It was my idea and I drove it; AI wrote most of the code. Code and README: github.com/ahk02x/certguard.
